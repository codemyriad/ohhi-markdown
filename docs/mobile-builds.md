# Mobile builds

How the Android and iOS apps are built: in CI on every app push to `main`,
and by hand on a Mac for iOS. Workflow:
[`.github/workflows/mobile.yml`](../.github/workflows/mobile.yml). The local
Android toolchain (SDK, NDK, emulator, `tauri android dev`) is in
[mobile-android.md](mobile-android.md).

## What the two apps are

Both are Tauri 2 mobile targets of the desktop app: the same
`apps/desktop/src-tauri` crate and the same `apps/web` build in the webview,
under the identifier **`md.ohhi`** (every target's id since 2026-10-16).
A phone has no folder to pick, no updater and no other app reading its files,
so the app behaves like the web app in a browser: its vaults live in the
webview's own storage (OPFS), a vault is started *in this browser* or arrives
from a share link or a device link, and the relay keeps it in step with the
other devices. On iOS that storage needs `createWritable()`, which WebKit has
from iOS 26, so iOS 26.0 is the minimum.

| | Android | iOS |
| --- | --- | --- |
| Project | `src-tauri/gen/android` (versioned) | `src-tauri/gen/apple` (versioned): `ohhi-desktop.xcodeproj`, scheme `ohhi-desktop_iOS` |
| Platform config | `tauri.android.conf.json` if any | `src-tauri/tauri.ios.conf.json`: identifier, minimum iOS version |
| Minimum OS | see mobile-android.md | iOS 26.0 |
| CI runner | `ubuntu-latest` | `macos-latest`, latest stable Xcode |

## How CI builds them

**Every push to `main` that touches `apps/desktop/**`, `apps/web/**`,
`libs/**` or the workflow builds both apps** (kind `debug`). Actions →
**Mobile builds** → *Run workflow* builds on demand and asks for the kind:

- **`debug`** (pushes, and the default): a debug-signed Android APK that
  installs on any device or emulator, and an unsigned iOS Simulator app. No
  secrets needed.
- **`release`**: a release Android APK (unsigned for now, so it does not
  install as is; see *Not done yet*) and, when all the Apple secrets below
  exist, a signed App Store build uploaded to TestFlight. Without them the iOS
  job still builds the Simulator app and says which secrets are missing.

Bursts collapse: a newer push cancels the run in progress. Both jobs take the
desktop release's build settings (`TEAM_HOST`, `DEFAULT_RELAY`,
`TEAM_SECRET_HINT`, `TEAM_NETWORK_NOTE`; see
[desktop-builds.md](desktop-builds.md#build-settings)), so a team build's
phone app defaults to the team relay and its CSP is pinned the same way. The
version is `<major>.<minor>.<run number>` (major and minor from
`tauri.conf.json`), so every build counts up: Android's `versionCode` is
`major·1000000 + minor·1000 + patch`, iOS's `CFBundleVersion` is the version.
The run number is this workflow's own; once it passes 999, bump `version`'s
minor in `tauri.conf.json` (or set `bundle.android.versionCode`), or Android
version codes start to overlap.

Cost: the Android job compiles Rust four times (one per ABI, for the
universal APK) on Linux minutes; the iOS job compiles once for the Simulator
(twice for `release` with secrets) on macOS minutes, billed at a multiple. If
the budget bites, drop the push trigger to a path filter on
`apps/desktop/**` or a nightly schedule.

### What lands where

Artifacts stay in the workflow run for 14 days; nothing is published as a
release or sent to the team host.

| Artifact | Contents |
| --- | --- |
| `ohhi-android-<kind>-<sha>` | `ohhi-<sha7>-universal-debug.apk` (or `-universal-release-unsigned.apk`): all four ABIs in one APK |
| `ohhi-ios-simulator-<sha>` | `ohhi-<sha7>-ios-simulator-arm64.zip`: `ohhi.app` for an Apple-silicon Simulator |
| `ohhi-ios-appstore-<sha>` | `ohhi-<sha7>-ios.ipa`, the signed App Store build (only for `release` with secrets); the same build goes to TestFlight |

- **Android:** `adb install ohhi-*-universal-debug.apk`, or open the file on
  the phone (allow installing from that source once).
- **iOS Simulator:** unzip, then `xcrun simctl install booted ohhi.app` and
  `xcrun simctl launch booted md.ohhi`. A Simulator build never runs on a
  device; devices get TestFlight.
- **TestFlight:** after Apple's processing (minutes to an hour) the build
  shows in App Store Connect › the app › TestFlight; add testers there.

## The iOS project (`gen/apple`)

`src-tauri/gen/apple` is generated by `tauri ios init` and **committed**, like
the Android project. The CI job uses it as is; it runs `tauri ios init` only
if the folder is missing. Regenerate it only on a Mac (the CLI's `ios`
commands do not exist in a Linux build of it), and after:

- a Tauri CLI upgrade whose iOS template changed, or a change to the crate
  name (`[package] name`/`[lib] name` in `Cargo.toml`, which names the
  project), the identifier or `bundle.iOS` in `tauri.ios.conf.json`;
- then refill the icons, which `init` resets to Tauri's own:

```sh
cd apps/desktop
rm -rf src-tauri/gen/apple
pnpm exec tauri ios init --ci
pnpm exec tauri icon app-icon.png --ios-color '#4f46e5'   # opaque: the App Store refuses alpha
git add src-tauri/gen/apple
```

`tauri icon` also rewrites `src-tauri/icons/` (and `gen/android`'s icons if
present); keep only the `gen/apple` changes if that is all you meant.

**Two quirks, both handled in `scripts/`:**

- **Xcode 27's SwiftPM.** Tauri compiles its own Swift package through
  swift-rs, which hands `swift build` the iOS SDK in a way Swift 6.4's default
  build engine (`swiftbuild`) overrides with the host macOS SDK; the build
  then fails in AppKit (`'OpenGLES/EAGL.h' file not found`).
  `scripts/ios-shims/swift`, first on PATH, adds `--build-system native` to
  `swift build` and passes everything else through. Drop it once swift-rs
  passes the flag itself.
- **`pod` and `idevicesyslog`.** Tauri's iOS tooling looks for both on PATH
  and otherwise runs `brew install cocoapods libimobiledevice`. The app uses
  no pods and the Simulator needs no device tools, so `scripts/ios-stubs/`,
  last on PATH, holds stand-ins that print and exit 1. A real one, if
  installed, wins.

**The iOS 27 SDK needs Tauri 2.12.** Apps built with the iOS 27 SDK (Xcode
27) must adopt the UIScene life cycle or UIKit aborts them at launch ("UIScene
life cycle is required for apps built with this SDK"). Tauri 2.11 (tao 0.35)
does not; Tauri 2.12 (tao 0.37) does, with no change to the project. Until
the repo's lockfiles move to 2.12, an iOS app built with Xcode 27 builds but
quits on launch. The bump:

```sh
cd apps/desktop/src-tauri && cargo update -p tauri --precise 2.12.4   # needs Rust 1.90+
# and @tauri-apps/cli ^2.12.3 (apps/desktop) + @tauri-apps/api ^2.12.0 (apps/web), then rush update
```

Tauri 2.12 needs Rust 1.90 or newer, so `rustup update stable` on every
machine that builds the desktop app.

## Building on a Mac

The Linux dev machine cannot build iOS. A Mac with Xcode can, without any
admin rights: everything goes into your home, nothing into Homebrew.

**The Mac in use:** a colleague's Mac mini, `chris@10.0.0.1` (Tailscale
name `mac-mini.example-tailnet.ts.net`; the short name does not resolve from
the Linux machine, so use the IP). SSH key auth works non-interactively
(`ssh -o BatchMode=yes chris@10.0.0.1`). macOS 27.0.1, Xcode 27.0
(27A266a), iOS 27 Simulators (iPhone 17 and others). The connection is
relayed, so keep transfers small.

### One-time setup (in `~`, already done on that Mac)

| What | Where | How |
| --- | --- | --- |
| Rust (stable) + `aarch64-apple-ios`, `aarch64-apple-ios-sim` | `~/.cargo`, `~/.rustup` | `curl … https://sh.rustup.rs \| sh -s -- -y --no-modify-path --profile minimal`, then `~/.cargo/bin/rustup target add aarch64-apple-ios aarch64-apple-ios-sim` |
| Node 22.12 | `~/.local/node` | the official `node-v22.12.0-darwin-arm64.tar.gz`, checked against `SHASUMS256.txt`, unpacked with `--strip-components 1` |
| Rush 5.153.0, pnpm 10.17.0 | `~/.local/bin` | `npm i -g --prefix ~/.local @microsoft/rush@5.153.0 pnpm@10.17.0` |
| XcodeGen 2.46.0 | `~/.local/xcodegen/xcodegen` | the release `xcodegen.zip`, unpacked as is. Not a symlink to another copy: XcodeGen finds its presets beside its own path, and a linked binary generates a project with no base settings (no app icon). |

Then, in every shell that builds: `source scripts/mac-ios-env.sh`. It puts
exactly those on PATH (plus the repo's shims and stubs), leaves Homebrew off,
and says what is missing.

### Each build

The repo is private and the Mac has no GitHub key, so do not clone: copy your
working tree over with rsync (one directory, re-synced after each change).

```sh
# from the Linux checkout (or worktree)
rsync -az --delete --exclude node_modules --exclude common/temp --exclude target \
  --exclude dist --exclude .git --exclude gen/apple/build ./ chris@10.0.0.1:ohhi-ios/

ssh chris@10.0.0.1 'cd ~/ohhi-ios && source scripts/mac-ios-env.sh &&
  rush install &&
  (cd apps/web && rushx build) &&
  cd apps/desktop &&
  pnpm exec tauri ios build --debug --target aarch64-sim --no-sign --ci'
# → apps/desktop/src-tauri/gen/apple/build/arm64-sim/ohhi.app
```

`tauri ios build` is the build to use, not raw `xcodebuild`: the project's
*Build Rust Code* phase calls back into the CLI (`pnpm tauri ios
xcode-script`), which reads its options from the running `tauri ios build`
and fails without one. `--target aarch64-sim --no-sign` builds for the
Simulator with no Apple account; drop `--debug` for a release build.

Run it in a Simulator, headless:

```sh
ssh chris@10.0.0.1 '
  xcrun simctl boot "iPhone 17"; xcrun simctl bootstatus "iPhone 17" -b
  xcrun simctl install booted ~/ohhi-ios/apps/desktop/src-tauri/gen/apple/build/arm64-sim/ohhi.app
  xcrun simctl launch booted md.ohhi
  xcrun simctl io booted screenshot ~/ohhi-shots/app.png'
rsync -az chris@10.0.0.1:ohhi-shots/ ./shots/
```

`simctl` cannot tap or type. To drive the app (tap a label, type into the
editor, dump the accessibility tree) a small XCUITest runner that attaches to
`md.ohhi` by bundle id works headless; one lives outside the repo at
`~/ohhi-uitest` on that Mac (`drive.sh "tapcontains:Start a vault;type:Notes;tap:Create vault"`).

After regenerating `gen/apple` there, copy it back and commit it:

```sh
rsync -az --exclude build --exclude Externals --exclude xcuserdata --exclude .tauri \
  chris@10.0.0.1:ohhi-ios/apps/desktop/src-tauri/gen/apple/ apps/desktop/src-tauri/gen/apple/
```

**A device build** (your own iPhone, not the Simulator) needs an Apple
development team: `APPLE_DEVELOPMENT_TEAM=<team id> pnpm exec tauri ios build
--target aarch64` with that team's certificate in the Mac's keychain. On a
shared Mac, prefer TestFlight from CI.

## TestFlight: the secrets

Seven repository secrets, all required for the signed steps; with any missing
the `release` run skips them and warns.

| Secret | What it is | How to make it |
| --- | --- | --- |
| `APPLE_TEAM_ID` | The 10-character team ID | developer.apple.com › Account › Membership details |
| `APPLE_CERTIFICATE` | An **Apple Distribution** certificate with its private key, as a base64 `.p12` | Certificates › + › Apple Distribution, with a CSR from Keychain Access; install it, export certificate and key as `.p12` with a password, then `base64 -i dist.p12 \| pbcopy` |
| `APPLE_CERTIFICATE_PASSWORD` | That `.p12`'s export password | |
| `APPLE_PROVISIONING_PROFILE` | An **App Store Connect** provisioning profile for `md.ohhi`, base64 | Identifiers › + › App ID with bundle ID `md.ohhi`; Profiles › + › App Store Connect, pick the App ID and the certificate; download, `base64 -i ohhi.mobileprovision \| pbcopy` |
| `APP_STORE_CONNECT_KEY_ID` | An App Store Connect API key's ID | App Store Connect › Users and Access › Integrations › App Store Connect API › + (role *App Manager*) |
| `APP_STORE_CONNECT_ISSUER_ID` | The issuer ID shown above that keys table | |
| `APP_STORE_CONNECT_KEY` | The key's `.p8` file contents (plain text, `-----BEGIN PRIVATE KEY-----` …) | Downloadable once, when the key is made; keep a copy in the password manager |

Also once: create the app record in App Store Connect (Apps › + › New App,
bundle ID `md.ohhi`), or the upload is refused. The signed build runs `tauri
ios build --target aarch64 --export-method app-store-connect` with the
certificate and profile (Tauri imports them into a temporary keychain), then
`xcrun altool --upload-app` with the API key placed at
`~/private_keys/AuthKey_<id>.p8` for the step and removed after.
`notarytool` is macOS-only and plays no part for iOS.

## Not done yet

- **Android release signing.** Release APKs are unsigned. To sign: a keystore
  (`keytool -genkey -v -keystore ohhi.jks -alias ohhi -keyalg RSA -keysize
  2048 -validity 10000`), stored as secrets (`ANDROID_KEYSTORE` base64,
  `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`),
  written to `gen/android/keystore.properties` in the job and read by
  `app/build.gradle.kts`'s `signingConfigs` (Tauri's Android signing guide);
  then an `.aab` (`--aab`) for Play. Losing that keystore means a new Play
  listing, so it lives in the password manager too.
- **iOS signing for anything but TestFlight.** No ad-hoc or development
  export; no Apple team chosen yet.
- **Store listings.** No Play Console or App Store listing, screenshots,
  privacy labels or review submission.
- **Real `.md` files in app storage.** Vaults live in the webview's OPFS, not
  as markdown files in the app's Documents folder (Files app, iCloud) or
  Android shared storage, so no other app or agent on the phone can read them,
  and the OS may clear them (iOS can evict website data). The share link and
  the relay are what keep a copy elsewhere.
- **Brand icon.** `apps/desktop/app-icon.png` is still the placeholder "E";
  both mobile icon sets are generated from it.
